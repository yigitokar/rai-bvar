\section{Related software, numerical oracles and licensing}\label{sec:related}

% ---------------------------------------------------------------- P1: packages in their Phase 0-2 roles
Several existing packages were named as numerical oracles or references. We list them with the role each actually had and the versions used; parity results are in \cref{sec:validation-parity}.
\begin{itemize}
\item The R package \pkg{BVAR} \citep{kuschnig2021bvar}, version 1.0.5 \citep{kuschnig2024bvar}, was run as the oracle for the hierarchical prior of \citet{giannone2015prior}, for the sum-of-coefficients and single-unit-root dummy observations, and for Metropolis--Hastings sampling of the hyperparameters. % [V] tests/parity/test_r_bvar.py; fixtures tests/parity/fixtures/r_bvar_*.json; tests/parity/BVAR_PARAMETRIZATION.md "Versions" (R 4.1.2, BVAR 1.0.5)
\item \pkg{stochvol} \citep{kastner2016dealing,hosszejni2021modeling}, version 3.2.1, was run as the oracle for univariate SV (the design document names 3.2.9, but the committed fixtures were generated with 3.2.1). % [V] tests/parity/test_stochvol.py; tests/parity/SV_PARAMETRIZATION.md "Versions"
\item \pkg{bayesianVARs} \citep{gruber2026bayesianvars}, version 0.1.8, was planned as the oracle for the corrected reduced-form sampler but could not be built in the development environment, which had no Fortran compiler (\code{gfortran}); we state no finding about it. The corresponding Phase~2 exit criterion was met by substitution: an exact system-wide Gibbs sampler written in R for this purpose serves as the reduced-form oracle. % [R] DESIGN.md Stage 4 amendment (2); SV_PARAMETRIZATION.md §4; fixtures probe_bayesianvars.nc (bayesianvars_available = 0) and bvars_swa_*.nc; tests/parity/test_bayesianvars.py
\item The Python package \pkg{bvar} of the Bank of England \citep{labonne2026bvar}, version 0.3.5 (MIT licence), is a second oracle for the analytic engine. % [V] tests/parity/test_boe_bvar.py; tests/parity/BOE_BVAR_NOTES.md header
\item \pkg{bvartools} \citep{mohr2026bvartools} was an architectural reference and was never run as an oracle. % [V] tools/make_r_fixtures.R loads only jsonlite, BVAR, coda, stochvol (l.87-92) and probes bayesianVARs
\end{itemize}
Oracles named for later phases are \pkg{factorstochvol} \citep{kastner2026factorstochvol}, \pkg{bvars} \citep{liu2026bvars}, \pkg{bsvars} \citep{wozniak2026bsvars}, \pkg{bsvarSIGNs} \citep{wang2026bsvarsigns} and \pkg{bvarsv} \citep{krueger2015bvarsv}; none is run in this release. % [R] SPEC.md §2.2 (Phases 3, 5, 6); the sources of some were read for constants (footnote below), so "run", not "used"

% ---------------------------------------------------------------- P2: other software, one neutral sentence

% ---------------------------------------------------------------- P3: what the package builds on
The MCMC engine is written in \pkg{JAX} \citep{bradbury2018jax,frostig2018compiling}, the analytic engine in \pkg{NumPy} \citep{harris2020array} and \pkg{SciPy} \citep{virtanen2020scipy}, forecasts and MCMC posteriors are returned as \pkg{xarray} objects \citep{hoyer2017xarray}, and the continuous ranked probability score (CRPS), its threshold-weighted version and the energy and variogram scores come from \pkg{scoringrules} \citep{zanetta2024scoringrules}; a comparable R package is \pkg{scoringRules} \citep{jordan2019evaluating}. % [V] pyproject.toml [project] dependencies; src/rai_bvar/evaluation/scores.py (sr.crps_ensemble, sr.twcrps_ensemble, sr.es_ensemble, sr.vs_ensemble); src/rai_bvar/forecast/result.py (xr.Dataset), src/rai_bvar/engines/mcmc/results.py (DataTree); analytic engine has no xarray posterior
Reference values for the convergence-diagnostic tests were computed with \pkg{ArviZ} \citep{kumar2019arviz} and hard-coded, and a further comparison runs only when \pkg{ArviZ} is installed; \pkg{ArviZ} is not a dependency. % [V] tests/unit/test_diagnostics.py docstring l.3-7; tests/mcmc/diagnostics/test_diagnostics_ext.py l.293 (pytest.importorskip("arviz")); pyproject.toml dependencies and dev group
The samplers are hand-written Gibbs kernels by design, not models in a probabilistic programming language such as \pkg{PyMC} \citep{abrilpla2023pymc} or \pkg{NumPyro} \citep{phan2019composable}. % [R] SPEC.md R7
Each kernel exposes its exact conditional or its Metropolis--Hastings acceptance ratio, on which the identity tests (\cref{sec:validation-u}) and the deterministic replay of failures (\cref{sec:architecture}) rely; we make no claim about how the two approaches compare in mixing. % [V] src/rai_bvar/validation/identities.py docstring; [R] DESIGN §5.7 (D-18: the host replays the failing chunk and evaluates the failing block's exposed conditional); no NUTS comparison exists in the repository (dossier 01, unsupported item 2)

% ---------------------------------------------------------------- P4: licensing and the practice, exact wording
\pkg{rai-bvar} is released under the Apache License, version 2.0. % [V] LICENSE; pyproject.toml license = "Apache-2.0"
The R oracles \pkg{BVAR} and \pkg{stochvol} are GPL-licensed, and the project's specification therefore requires algorithms to be implemented from the published papers, not translated from GPL source. % [R] tests/parity/BVAR_PARAMETRIZATION.md l.3 (GPL-3); docs/phase2/03_sv_outliers_t.md l.9 (stochvol GPL >= 2); SPEC.md §2.1
\todo{Confirm the licence of each R package named in this section on CRAN at submission (dossier 01, section 4.2).}
The development practice is stated as follows:
\begin{quote}
No code was translated from GPL sources. Algorithms were implemented from the published papers. GPL packages were run as numerical oracles, and in a few documented cases (named in the repository notes) their source was read to pin down an oracle's behaviour, defaults or constants, never to write implementation code.
\end{quote}
% [V] wording verbatim from dossier 01 §6.2; the practice is recorded in the notes listed in the footnote
Not every package whose source was read is an oracle of this release: the notes also record reading the sources of \pkg{bayesianVARs}, \pkg{bvarsv}, \pkg{bvartools}, \pkg{factorstochvol} and \pkg{bsvars} to confirm published constants and observable behaviour. % [R] docs/phase2/01_omori_mixture.md l.9-11; docs/phase2/02_sv_sampler.md l.597-608
This is weaker than a clean-room process in the strict sense, in which implementers never see the source, and we do not claim that stronger property.
Five repository notes record a reading of GPL source,\footnote{%
\code{docs/phase2/02_sv_sampler.md}: the sources of \pkg{stochvol} 3.2.9, \pkg{bayesianVARs} 0.1.8 and \pkg{bvarsv} 1.1, read for behaviour and constants;
\code{docs/phase2/01_omori_mixture.md}: the published mixture constants and observable behaviour, confirmed in six GPL packages;
\code{docs/phase2/03_sv_outliers_t.md}: text searches of the \pkg{stochvol} sources, and of a MATLAB replication code by Carriero, Clark, Marcellino and Mertens that carries no licence;
\code{docs/phase2/07_jax_patterns.md}: a search of one \pkg{stochvol} header for the ten published mixture constants, in a cross-check;
\code{tests/parity/BVAR_PARAMETRIZATION.md}: the R sources of \pkg{BVAR} 1.0.5, read to establish its behaviour.}
% [V] docs/phase2/02_sv_sampler.md l.6, l.597-608; 01_omori_mixture.md l.9-11; 03_sv_outliers_t.md l.6-9; 07_jax_patterns.md l.736, l.764; tests/parity/BVAR_PARAMETRIZATION.md l.3-13
and \cref{app:licensing} lists them with the version read and the purpose, together with the notes in which no GPL source was read.
